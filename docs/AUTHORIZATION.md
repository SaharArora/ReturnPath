# Authorizing the three real apps on your Mac

This is a single-merchant, controlled test setup, not a public multi-tenant product. Primary references are in SETUP_SOURCES.md. No credentials have been created or accounts connected by this handoff.

## 1. What each login does

| Connection | Purpose | Credential used by ReturnPath |
|---|---|---|
| Codex/ChatGPT sign-in | Lets the coding assistant work | Not an application API credential |
| GitHub authorization | Clone/push or permit a cloud coding checkout | Does not authorize Gmail, Slack or Stripe |
| Gmail API | Read support requests; send verification/outcome messages | Desktop OAuth client JSON + user-granted token JSON |
| Slack Web API | Post/update and read back demo operations messages | Installed bot OAuth token |
| Stripe API | Test payment/refund and reconciliation | Sandbox/test secret API key |
| Model API | Run the app's bounded interpreter | Separate configured model-provider API key |

Existing Gmail/Slack accounts are useful, but being signed into their websites is not API authorization for Python. ChatGPT connectors do not automatically supply tokens to your repository. App-level provider credentials must be configured explicitly. ChatGPT and API billing are separate.

## 2. Create the private local configuration

Follow Section E of SETUP_MAC_AND_CLOUD.md. Default files:

```text
~/.config/returnpath/returnpath.env
~/.config/returnpath/gmail-client.json
~/.config/returnpath/gmail-token.json   # generated by browser authorization
```

Use a dedicated support Gmail mailbox and a separate controlled customer mailbox. The customer account only needs to send email/click the scoped verification link; it need not be authorized to the app. The Gmail API support token can read the support mailbox: a query filter does not reduce its OAuth authority.

After M0, `make init-config` preserves existing values, creates missing session settings and prompts locally for an operator-login password without echo; it stores a salted hash rather than your plain password. Fill `RP_SUPPORT_EMAIL` and `RP_CUSTOMER_EMAIL` locally. Keep `RP_ALLOW_CONNECTED_WRITES=false` until ready for a specifically authorized test.

## 3. Stripe — you do not need a live merchant deployment

Stripe documents that testing is available after account creation, before activating live payments. Create an account and use its testing environment; do not move real money. If the provider requires additional signup checks for your account, complete genuine required verification or report the blocker, rather than fabricate business details.

1. Open `https://dashboard.stripe.com/register` and create/sign into your account. Verify the email/account as requested.
2. In the Dashboard, select a **Sandbox** or **Test mode** context, depending on the account's current UI. Keep all demonstration objects in the same context. Do not activate live payments solely for this demo.
3. Open **API keys** (through the Dashboard's developer/Workbench controls or search).
4. Reveal/copy the **test secret key**, not the publishable key. The common prefixes are `sk_test_` for secret and `pk_test_` for publishable. Do not use `sk_live_`, a webhook signing secret, or a live restricted key.
5. Paste the secret only into your private configuration as `STRIPE_SECRET_KEY=...`. Leave it out of screenshots and chat. Restricted test keys can be used when their required permissions are verified; do not invent a permission list or select a live key to fix access.
6. After M0 exists, run `make doctor SERVICE=stripe`. The program should identify the actual account/test context without creating objects. Record the intended nonsecret account ID in `RP_STRIPE_ACCOUNT_ID` after confirming it belongs to this test setup.
7. Later, once writes are explicitly enabled and guards pass, `make connected-seed` creates an isolated $100 TEST card payment, stores the real charge ID, and creates the approved $30 return record. The application uses provider test instruments—not real card numbers.
8. The core demonstration creates a real Stripe API refund object in that testing environment and retrieves it after worker restart. Its UI and evidence must explicitly say TEST; it is not a real cash refund.

No checkout page, Stripe Connect platform, billing subscription or production bank settlement is needed by this design. API reachability/test auth alone does not complete the integration; the guarded partial refund and recovery must actually run. Event eligibility for test-mode use is a separate organizer question.

## 4. Slack — install a small bot in a private channel

Use a workspace you own or where you have permission to install this app. Merely being a member does not guarantee install rights. Follow the workspace's approval process rather than bypassing it.

1. Create a private channel named `returnpath-demo` in that workspace. Put no unrelated work conversations there.
2. Open `https://api.slack.com/apps` and choose **Create New App → From a manifest**. Choose the intended workspace.
3. Paste the YAML from `config/slack-app-manifest.yaml`, review permissions, and create the app.
4. The manifest defines a ReturnPath bot and these scopes:
   - `chat:write`: post/update case messages.
   - `groups:read`: inspect allowed private-channel metadata/access.
   - `groups:history`: read back case evidence in private conversations the bot is authorized to access.
5. Open **OAuth & Permissions → Install to Workspace** (or the current equivalent) and approve installation. Copy the **Bot User OAuth Token**, normally beginning `xoxb-`, into `SLACK_BOT_TOKEN` in your private local config. Do not use an app-level `xapp-` token or a user token instead.
6. Invite the ReturnPath bot into the private channel using the channel's add-app/invite control, e.g. `/invite @ReturnPath`. Installing to the workspace is not the same as joining the private channel.
7. Copy the channel's actual ID from its details or copied channel link and store it as `RP_SLACK_CHANNEL_ID`. Use the ID, not `#returnpath-demo`.
8. After M0 exists, run `make doctor SERVICE=slack`. It should check `auth.test` and allowed channel access. The later connected workflow must actually post/update/read back a case message; doctor alone does not prove posting works.

No Slack Events API callback, Socket Mode, slash command or public tunnel is needed for this outbound Web API baseline. Do not build Bolt event handlers or a multi-workspace OAuth website just to post to your own workspace. If scopes change, reinstall/reapprove the app so the token grant matches.

## 5. Gmail — local Desktop OAuth with explicit consent

Use a Google account you control; a managed university/work account may restrict OAuth or project creation. Prefer a dedicated support test mailbox. This setup uses Google's development/testing path, not a claim of production verification.

1. Open `https://console.cloud.google.com/`. Create/select a Google Cloud project named `ReturnPath Hackathon`. A project is the configuration container for Gmail API access; this does not deploy the application to Google Cloud.
2. Open **APIs & Services → Library**, find **Gmail API**, and enable it.
3. Open **Google Auth platform → Branding**. Start configuration with the app name `ReturnPath`, your support/contact email and the genuine required details.
4. For a personal Gmail account choose **External** audience and keep the publishing status **Testing**. **Internal** is for an eligible Workspace organization, not a generic safer option for personal accounts.
5. Under **Audience → Test users**, add the exact support mailbox that will authorize the app. The ordinary customer mailbox does not need to be added unless it will also grant OAuth access.
6. Under **Data Access**, add exactly the Gmail scopes the baseline needs:

```text
https://www.googleapis.com/auth/gmail.readonly
https://www.googleapis.com/auth/gmail.send
```

Do not add mailbox deletion/full access, Drive, Calendar, or domain-wide delegation. This read scope is broad within the authorized mailbox; use a dedicated mailbox and an allowlisted query. Development/testing has a documented verification exception, but test-user restrictions and possible warnings still apply.

7. Under **Clients → Create client**, choose **Desktop app**, name it `ReturnPath Local`, and create/download its JSON. Do not choose Web application for this local loopback flow and do not create a service-account JSON.
8. Save the downloaded file as:

```text
~/.config/returnpath/gmail-client.json
```

You can use a Finder Save/Move dialog with Command-Shift-G to access that folder. Keep the downloaded credentials out of the repository. Restrict permissions:

```bash
chmod 600 ~/.config/returnpath/gmail-client.json
```

9. After Codex implements M0, run:

```bash
cd ~/testingxd
make setup
make init-config
make auth-gmail
```

The helper must open your Mac browser and use an official loopback OAuth flow. Select the exact support account, inspect the scopes and grant consent to your own test app. An expected test-app warning is not proof of a production-approved app; do not bypass a managed-account restriction or authorize an unknown app.

10. The helper saves `gmail-token.json` securely, checks mailbox identity and performs only read-only validation. You do not type a Gmail password into Python and do not manually paste tokens into Codex. Run `make doctor SERVICE=gmail` afterward.

In Google's External/Testing configuration, refresh tokens for these Gmail scopes generally expire after seven days under the documented policy; they can also be revoked earlier. On `invalid_grant`, reauthorize through the helper rather than marking Gmail connected or publishing the OAuth app just to avoid expiry. Switching scopes also requires an appropriate renewed grant.

The local callback works because the authorization helper and browser are on the same Mac. A cloud container's `localhost` is not your Mac. Keep this OAuth step and real-provider demo local.

## 6. Model API — separate from your Codex subscription

For an OpenAI-backed interpreter, create/use an authorized API project key through `https://platform.openai.com/`, configure API billing/access as needed, and enter it locally as `OPENAI_API_KEY`. Select a model available to that API project in `RP_MODEL`; Codex should verify the configured model rather than inventing an unavailable identifier. No specific paid tier or model is required by the handoff.

Your ChatGPT/Codex plan does not automatically provide the application's API usage. Configure a modest provider budget/alerts and enforce per-contact/model-call limits in the app. Do not claim a provider alert is a hard spending cap. Local simulator tests use no model API and must remain available without this key, but a real model run is required for connected submission evidence.

## 7. First end-to-end run after implementation

After local safety tests pass, fill the private config and intentionally set:

```text
RP_MODE=connected-test
RP_ALLOW_CONNECTED_WRITES=true
RP_ENABLE_VOICE=false
```

Confirm support/customer addresses, Slack channel, Stripe test account, and enabled write limits. Start a fresh fixture only once with `make connected-seed`, then `make connected-dev`. From the controlled customer account send a real message to the support inbox:

```text
Subject: [ReturnPath Demo] Order 4127
I returned the headphones from order 4127 and still haven't received my refund.
```

Use the actual seeded reference if it differs. Open the scoped verification email in the customer mailbox on this same Mac and explicitly confirm. The agent must execute only after verification/policy checks. Observe Stripe TEST state and Slack case evidence. For crash recovery, arm the named boundary and restart the worker without reseeding.

Return `RP_ALLOW_CONNECTED_WRITES=false` after tests. Do not expose this laptop service publicly for Gmail/Slack/Stripe; these integrations use outbound API calls. The same-laptop verification URL does not constitute a deployable remote-customer service. Twilio or remote access would require an explicitly secured public endpoint and is optional later.

## 8. What must remain unclaimed

Accounts created is not integrations verified. Tokens stored is not workflow completed. Real Stripe test API calls is not live-money usage. A passed simulator suite is not three external integrations. ReturnPath's authentication/safety design is a prototype, not production security certification. Report actual status and blockers.
